# Reference Test Design

This document is the high-level test matrix for the CPU spectral reference
integrator. It is intentionally not a spec file. The goal is to make each
canonical pipeline stage independently testable before the CLI and shader
parity work are designed around it.

The canonical stage input/output contract lives in
[Stage Contracts](stage_contracts.md). The code rationale lives in
[Code Design](code_design.md), and the implementation sequence lives in
[Plan](plan.md). Source-to-decision traceability lives in
[Reference Decision Log](references.md).

## Test Stance

Every canonical stage must be runnable on its own:

```js
const nextPacket = integrator.runStage(stageId, packet);
```

The full ray trace must be equivalent to manually composing the same public
stages in canonical order. No stage should depend on hidden mutable class state
from a previous run.

Use four kinds of expected results:

- `analytic`: exact or closed-form values, such as `T = exp(-beta * distance)`.
- `invariant`: properties that must always hold, such as nonnegative radiance.
- `reference-data`: comparison to an external source after inputs are locked.
- `cross-model`: globe and flat adapters agree when configured to equivalent
  local conditions.

Initial tolerances should be strict for algebraic tests, moderate for numeric
integration convergence, and loose only for external clear-sky comparisons
where configuration differences are not yet fully controlled.

## Domain-First Expectations

This is a hard rule for the reference integrator: tests must assert real domain
expectations, not the current code shape.

Every stage test should start from one of these sources of truth:

- the physics or math being modeled
- a public API contract we intentionally designed
- an analytic known answer
- an invariant that must hold for any valid implementation
- pinned external reference data with fully specified inputs

Do not derive an expected result from the production implementation, a helper
that the stage happens to call, or a number chosen because it matches current
behavior. That creates circular tests and can bless exactly the magic-number
or accidental-architecture problem this reset is meant to remove.

Implementation helpers are allowed, but they are not decision makers. For
example, a vector utility can be tested directly in `utils.spec.js`; a
`validateRequest` stage test should instead state the domain expectation that
a ray direction is an orientation vector and that the validated packet contains
a finite unit direction for downstream distance math. The test should not care
whether the stage used a particular helper to get there.

When turning a pending shell into a real test, write the input and expected
output first, then name why that output is correct. If the reason is "because
the current code does it", stop and replace it with a domain reason before
implementing. Test names that mention private helper choices are a warning
sign unless the helper itself is the unit under test.

## Expected Value Policy

Prefer expected values that are pinned directly in the test or fixture:

- values copied from an authoritative reference table, metadata row, checksum,
  or standard
- values hand-computed from a tiny closed-form case and written as literals
- values from a published example with the reference and assumptions recorded
- values generated by an independent external tool or authoritative data source,
  stored as a fixture artifact with the exact tool/source version, input config,
  command, and provenance

It is acceptable to generate expected data from an independent external source,
such as a standards dataset, published tool, or separately validated
radiative-transfer package. It is not acceptable to create a second new local
implementation whose output justifies the first implementation. That only gives
us two untrusted pieces of code that may share the same misunderstanding.

Every expectation row must carry a canonical `reference` object, even when the
row is justified by a local design contract rather than external physics. The
object must include `id`, `kind`, `title`, `url` or `path`, `locator`, and
`derivationSummary`. Design constraints are allowed to point at local design
docs, but that only moves the justification boundary to the design document;
the design itself should still explain why the constraint exists.

Every expected datum must also carry a nearby derivation note. In specs this
should usually be a short comment. In JSON fixtures, where comments are not
available, make provenance part of the data itself. Exact numeric arithmetic
can live beside each value as `expected.<quantity>.derivation`. The note can be
short, but it must be enough for a reviewer to locate the source or reproduce
the hand derivation: equation name/number, reference section, table row,
metadata field, external tool version/config path, or fixture provenance. This
applies to inline literals, fixture rows, generated fixture outputs, checksums,
and image/sample expectations.

Fixture-backed assertions may omit assertion-site comments only when the
fixture row itself carries the full oracle metadata. That means every row has
stable identity, source class, canonical reference, assumptions, inputs,
expected output or expected error, units or semantic kind, derivation or
provenance, tolerance or structural comparison policy, and an independence
note. If a spec adds a direct assertion that is not simply comparing the
fixture-owned expected value, add a nearby reason/source comment in the spec.
This applies to stage descriptor checks, prerequisite errors, helper behavior,
stage history, immutability, adapter calls, packet-shape checks, and metadata
counts.

For any code or test backed by a physical property, include a reference and a
short description of what the reference supports. The description must be
specific enough to separate source-backed physics from local policy. For
example, PBRT Rays supports the idea that a ray has a finite origin and
direction, while this integrator's near-zero direction threshold is a local
numerical stability policy layered on top of that ray model. API ownership
rules, such as "physical coefficients belong to the model bundle", should cite
the project design instead of pretending to be an external physics fact.
Secondary sources may be used to keep early tests moving, but mark them as
secondary in the reference log. Before a physics-backed value, constant, or
validation range becomes package-facing, chase down the primary source or
record why the secondary source is intentionally retained.

Implementation code has the same traceability rule as tests. Each meaningful
algorithm choice and branch needs a nearby source breadcrumb when it becomes
real behavior: positive computations, empty/default/fallback paths, validation
rejects, optional-field behavior, ownership boundaries, numerical tolerances,
rounding, and packet-preservation choices. Comments should name why the branch
exists and where the rationale is owned. If a branch introduces or clarifies a
policy, update the owning source/design document before treating the stage as
complete.

For analytic tests, pin the numeric expected result when it is simple enough:

```js
// Expected: PBRT transmittance, homogeneous Beer-Lambert.
// Derivation: tau = sigma_t * d = 0.2 / km * 3 km = 0.6; T = exp(-0.6).
expect(result.viewOpticalDepth.tauByWavelength).toEqual([0.6]);
expect(result.viewOpticalDepth.transmittanceByWavelength[0])
	.toBeCloseTo(0.5488116360940264, 12);
```

Using a standard primitive such as `Math.PI` in a literal expression may be
acceptable for readability, but avoid calling production helpers or newly
written local reference calculators to compute expected values inside the test.
If a large table of expected values must be generated, generate it once from a
named independent external source, check it in as fixture data, and make the
provenance visible in [Reference Decision Log](references.md).

### Expectation Intake Checklist

Before turning a pending shell into a real test, write down:

- `quantity`: what physical or API quantity is being checked.
- `source class`: `hand-derived analytic`, `authoritative table`,
  `metadata/checksum`, `published example`, or `external-tool fixture`.
- `source`: citation, URL, DOI, tool name, or standard.
- `assumptions`: units, geometry, wavelength grid, atmosphere profile, source
  model, surface model, numerical method, and sign convention.
- `expected value`: literal value, checked fixture row, checksum, or fixture
  artifact path.
- `reference`: for JSON fixtures, the canonical object with `id`, `kind`,
  `title`, `url` or `path`, `locator`, and `derivationSummary`.
- `derivation note`: the nearby code comment or fixture data field that names
  the equation, table, metadata field, tool/config, or provenance record used
  to produce the expected datum.
- `tolerance`: exact, decimal places, absolute, relative, or convergence rule.
- `comparison policy`: for nonnumeric expected values, the exact structural or
  semantic comparison rule.
- `review note`: why this expectation is independent of the implementation.

If any of those fields are unclear, the test can stay pending until the
expectation is defensible.

## Validation Scope

In this project, "validation" means comparing inputs, intermediate values, or
outputs against a stated domain expectation. The source of that expectation
depends on the stage:

- `validateRequest` validates the request envelope against physical-unit
  sanity, model-interface contracts, and numerical-control limits. It does not
  validate radiance, optical depth, or sky color yet.
- Transport and scattering stages validate computed values against physical
  equations, analytic invariants, independently generated fixtures, or
  documented numerical-convergence limits.
- Fixture-shape tests validate that expected data carries enough provenance,
  assumptions, derivation notes, and tolerances to be a defensible oracle.

So the first stage's red tests should fail because the code does not yet reject
invalid physical/numerical inputs or produce the canonical validated request.
Later red tests should fail because the code does not yet match Beer-Lambert,
phase normalization, single-scattering, Lambertian reflection, or other
physical expectations.

## Analytic Invariant Test Pattern

The first validation layer is an analytic invariant spine: tiny artificial
physics fixtures where the expected answer is known without trusting the
implementation, an external library, a shader, or a captured image.

Do not start these tests with Earth, a real sky, PDAS tables, CIE tables,
ASTM G-173, SMARTS, or libRadtran. Start with toy domains whose math fits in
the test name or a short comment.

For every analytic invariant test:

1. Build the smallest packet or request that exercises the stage.
2. Use deliberately simple values.
3. Write the expected output as pinned literals from the closed-form equation
   or invariant.
4. State why that output is correct in the test name, a short derivation
   comment next to an inline expected literal, or a structured derivation field
   beside a fixture row.
5. Confirm the test fails against placeholder or missing behavior.
6. Implement only enough stage behavior to satisfy that domain expectation.

Useful first fixtures:

- `vacuum`: `sigma_t = 0`, any distance -> `tau = 0`, `T = 1`.
- `zeroLengthPath`: distance `0` -> `tau = 0`, `T = 1`.
- `homogeneousMedium`: constant `sigma_t`, distance `d` ->
  `tau = sigma_t * d`, `T = exp(-tau)`.
- `splitPath`: collinear segments `a->b` and `b->c` ->
  `T(a,c) = T(a,b) * T(b,c)`.
- `isotropicPhase`: `P = 1 / (4 * pi)` and integrated phase equals `1`.
- `singleScatteringOneSample`: one sample with known scattering coefficient,
  phase, source value, transmittance, and step length -> contribution equals
  the product of those factors.
- `blackLambertianSurface`: albedo `0` -> reflected surface radiance `0`.
- `whiteLambertianSurface`: albedo `1`, direct irradiance `E`, normal
  incidence -> `L = E / pi` before view attenuation.

Stage seeds:

- `sampleViewPath`: midpoint sample locations are deterministic, ordered, and
  weights sum to path length.
- `evaluateMedium`: vacuum returns zero coefficients; homogeneous medium
  returns the same coefficient at every sample.
- `integrateViewOpticalDepth`: vacuum, zero length, homogeneous
  Beer-Lambert, monotonicity, and split-path multiplicativity.
- `integrateSolarTransmittance`: the same transmittance math on source paths,
  plus source visibility only after geometry is explicit.
- `evaluateScatteringPhase`: isotropic value, phase normalization, and named
  angle convention before Mie/Rayleigh approximations become complex.
- `integrateSingleScattering`: one-sample product test before any full sky ray.
- `resolveSurfaceRadiance`: Lambertian closed forms before diffuse sky.
- `composeSpectralRadiance`: wavelength-by-wavelength sums and nonnegative
  component checks.

For example, prefer a pinned Beer-Lambert transmittance literal such as
`0.5488116360940264` with a comment saying it comes from PBRT's homogeneous
Beer-Lambert transmittance equation and equals `exp(-0.6)`, rather than
computing the expected value through a new helper. Calling the production
helper being tested, such as a future `computeTransmittance()`, to compute the
expected value is circular and not allowed.

## Reference-Mined Verification Ranges

Use these as sanity checks and expected-value seeds while building the real
stage tests. They do not replace analytic known-answer tests. A verification
range should only fail a run when the run configuration matches the reference
assumptions that produced the range.

### Hard Invariants

These can be enforced for any physically valid run:

- Transmittance is always in `[0, 1]`.
- Vacuum or zero-length transport gives optical depth `tau = 0` and
  transmittance `T = 1`.
- With nonnegative extinction, optical depth along a ray is nondecreasing and
  transmittance is nonincreasing.
- Transmittance is multiplicative along collinear path segments:
  `T(a,c) = T(a,b) * T(b,c)`.
- Homogeneous-medium transmittance follows Beer-Lambert:
  `T = exp(-sigma_t * distance)`.
- Phase functions integrate to one over solid angle.
- The isotropic phase value is `1 / (4 * pi) ~= 0.0795774715 sr^-1`.
- Henyey-Greenstein `g` must be inside `(-1, 1)`; `g = 0` becomes isotropic.
- Radiance, irradiance, scattering, absorption, extinction, density, sample
  weights, and optical depths are nonnegative unless a deliberately signed
  diagnostic quantity is being tested.
- Linear RGB may be below zero or above one after XYZ conversion; display
  clipping, exposure, and tone mapping are outside the reference integrator.

Sources: PBRT transmittance and phase-function chapters.

### Solar Source Sanity

Use these to catch wrong units, distance scaling, and solar-spectrum mistakes:

- The IAU nominal total solar irradiance at `1 au` is `1361 W/m2`. Treat this
  as a conventional full-spectrum anchor for Sun-like source configuration,
  not as a visible-band integral.
- Top-of-atmosphere spectral irradiance integrated over the full solar source
  table should be near the configured total solar irradiance. A 360-830 nm
  visible-range integration must be lower and should not be forced to equal
  `1361 W/m2`.
- Distant Sun direct irradiance at a surface should scale with
  `max(dot(normal, sunDirection), 0)`.
- Local finite Sun irradiance should follow inverse-square distance scaling
  when solar radiance and radius are held fixed.
- For a small local finite Sun, the solid angle should approach
  `pi * (radius / distance)^2`.

Sources: IAU Resolution B3 for the nominal solar irradiance, NREL/NLR
ASTM G-173 for spectral irradiance table structure, and the local finite-source
solid-angle limit from geometry.

- elevation `10.0 deg`: relative optical air mass `5.5841`

### Flat Large-Lateral-Path Checks

Flat-world atmosphere tests need a separate lateral-path category. A globe
near-horizon ray and a flat near-horizontal ray are not interchangeable:
curvature can let the globe ray leave the dense atmosphere, while a flat slab
ray can remain inside the same altitude layer until it reaches a named side
boundary.

Expected test rules:

- A flat horizontal ray in an unbounded slab is invalid for transport because
  the atmosphere segment is infinite.
- A flat horizontal or near-horizontal ray with a finite disk/patch/dome
  boundary must report that boundary reason and its path length.
- For a homogeneous flat slab, optical depth along that finite lateral path is
  still the Beer-Lambert result `tau = sigma_t * lateralDistance`, so large
  flat-world extent should produce large attenuation without introducing any
  new scattering constant.
- For an exponential vertical profile sampled at nearly constant altitude, a
  flat horizontal path should accumulate approximately constant-density
  optical depth until the named boundary is reached.
- Local-Sun sample-to-source paths need the same treatment: if the source path
  stays inside the slab for a long lateral distance, the diagnostics should
  expose the long source optical depth instead of hiding it behind source
  strength calibration.

Source basis: PBRT transmittance for path-integrated optical depth, the local
flat-world geometry contract for named finite boundaries, and Kasten/Young only
for Earth-like low-elevation air-mass comparison rows. Any actual flat-disk
radius or lateral extent remains a model hypothesis that must be named and
recorded before it becomes a fixture value.

Follow-up: flat-world lit-terrain visibility depth.

The flat/local-Sun model also needs a visibility-depth probe for terrain seen
through dense near-horizontal atmosphere. A terrain point is visible only after
both legs are accounted for: source light reaching the terrain through the
flat atmosphere, and terrain radiance returning through the view path. For
in-scattered airlight, each view sample similarly needs its own source path to
the Sun or to a named source boundary. This follow-up should report distance
curves for direct terrain signal, source-path transmittance, view-path
transmittance, in-scattered airlight, and contrast against the intervening
haze/background.

The follow-up should keep finite/distant Sun behavior separate from atmosphere
path thickness. A directional Sun may use fixed top-of-atmosphere irradiance;
a finite local Sun must expose any inverse-square or solid-angle falloff, and
any renormalization back to Earth-like irradiance must be a named model
property. There should be no hidden ambient light: if direct Sun, diffuse sky,
lunar, stellar, artificial, and emissive terms are all absent or extinguished,
near terrain may legitimately be dark.

If the probe shows that terrain contrast/detail is functionally unrecoverable,
the renderer may use a named low-detail visual proxy instead of physically
resolving terrain texture at that distance. That approximation must be
diagnostic-facing: record that detail is being replaced because the modeled
signal is below a visibility/contrast threshold, not because an unowned ambient
or texture fade was introduced.

Initial implementation note: `run-reference-probe.js --light-extent` now
covers the source-path classification slice of this follow-up. It reads named
scenario sets from
`scripts/flat/atmosphere_rejected/data/reference/light-extent-scenarios.json`, samples a
straight path from a finite Sun through a simple flat atmosphere profile, and
reports two independent thresholds:

- `opacityLossFraction`: how much source-path transmittance has been lost.
- `usefulLightLossFraction`: how much effective irradiance has been lost
  after both transmittance and finite solar-disk solid-angle falloff.

Both thresholds are configured as loss fractions in `[0, 1)`. Values near `1`
mean almost nothing remains; exact `1` is intentionally invalid because
Beer-Lambert transmittance approaches zero asymptotically. This probe does not
yet decide terrain visibility because it does not include terrain albedo,
surface normals, view-path attenuation, in-scattered airlight, or contrast
against the background. Treat it as regime classification evidence for the
next terrain-visibility probe.

The first user-control bridge is explicit in the scenario schema:
`sun.brightnessScale` scales absolute effective irradiance, while
`sun.elevationDeg` sets the path angle above the flat horizon, and
`sun.directLightAvailable` can disable direct source contribution while keeping
the configured source brightness visible in diagnostics. Because the current
loss thresholds are relative loss thresholds, brightness does not change the
reported relative crossing distances yet; it only changes absolute irradiance
values. Elevation can change the crossings immediately because it changes how
quickly the source path exits dense near-surface air. Full terrain visibility
should add an absolute brightness, exposure, or contrast threshold before
using a user brightness setting to decide whether terrain detail survives.

Calculated effective-irradiance floors are now allowed as separate named
engineering anchors under `floors.effectiveIrradiance`. These floors are not
perceptual visibility thresholds and do not replace the relative-loss
crossings. They let us compare named app and real-Sun configurations against
quantities we can calculate and review:

- `app.flatDefaults.onePermilleMiddayEffective` is `0.1%` of the current app
  flat closest-false-sun source term:
  formula `0.001 * solarIrradianceScale 58 * solidAngle(25.749504 km, 5050.674164842701 km)`;
  value `0.000004736087535019212 app-effective-source-units`.
- `realSun.sanJose.onePermilleToaIrradiance` is `0.1%` of the app
  globe-simulation real-Sun top-of-atmosphere irradiance for the named San
  Jose pose, about `1.3195 W/m2` for the current midday and midnight defaults.

The first app-linked set inventory covers `app.flatDefaults.midday`,
`app.flatDefaults.midnight`, `realSun.sanJose.midday`, and
`realSun.sanJose.midnight`. The flat opposite-pose set is deliberately named
as an app default, not as physical midnight: with the current 3000-mile-high
false Sun it is still about `20.1 deg` above the San Jose flat horizon. The
real-Sun midnight set is the contrast case: the top-of-atmosphere source value
stays defined, but direct light is unavailable because the Sun is below the
local globe horizon.

Incorporating this probe into the running app is plausible as a
configuration-time calculation. It should not run per pixel or per frame.
Instead, a future adapter can run it when relevant user controls or atmosphere
presets change, cache the result by physical configuration, and give the
renderer derived values such as useful-light extent, opacity extent, and curve
samples. That preserves the probe's role as a diagnostic/classifier while
still letting the app react to user-configurable Sun elevation and later
brightness/contrast floors.

### Rayleigh And Wavelength Behavior

Use these as relationship tests before pinning full numeric atmosphere
profiles:

- Rayleigh scattering should increase toward shorter wavelengths according to
  the configured molecular model. For the common `lambda^-4` simplification,
  `beta_R(450 nm) / beta_R(650 nm) = (650 / 450)^4 ~= 4.35`.
- The Rayleigh angular phase should be symmetric in forward/backward direction
  for the same absolute scattering angle.
- Pure Rayleigh with equal source spectrum and equal path conditions should
  produce stronger blue in-scattering than red in-scattering.
- Any wavelength exponent, depolarization correction, or refractive-index
  correction must be a named model property, not a hidden color constant.
- Bucholtz Table 4 can seed numeric Rayleigh optical-depth fixtures after the
  chosen model atmosphere is explicit. For the `1962 U.S. Standard`
  atmosphere, safe-to-pin rows from the source page include `tau = 8.645e-3`
  at `1.00 um` and `tau = 7.788` at `0.20 um`.
- Do not pin visible red/blue Rayleigh optical-depth rows from the current HTML
  table scrape until the PDF/table export is inspected, because repeated
  scientific-notation exponents are visually compressed in the page text.

Sources: Bucholtz, Applied Optics 34, 2765-2773 (1995), DOI
`10.1364/AO.34.002765`, plus the simpler Rayleigh wavelength relationship and
Bruneton's warning against arbitrary unphysical solar/color constants.

### Reference Implementation Discipline

Bruneton's new implementation is useful less for copyable values and more for
verification discipline:

- check dimensional homogeneity of expressions
- keep solar spectrum configurable instead of a constant arbitrary spectrum
- convert spectral results through CIE/luminance or compare against full
  spectral CPU renderings
- unit-test shader/math behavior against a CPU reference
- avoid ad-hoc constants that only work for one planet or one coordinate map

Use this as a review checklist whenever a test or implementation introduces a
new numeric constant.

## Stage-By-Stage Test-First Workflow

Implement the reference one canonical stage at a time. For each stage:

1. Keep the prior stages passing.
2. Add or update pending test shells for the next stage in the current
   pipeline spec, then fill in that stage's unit tests before implementing the
   stage's physical behavior.
3. For each real test, document or encode the domain reason for the expected
   result before writing implementation code.
4. Confirm the new tests fail because the stage still returns placeholder or
   missing behavior, not because the test harness is malformed.
5. Implement only enough stage behavior to satisfy those tests.
6. Add or update diagnostics for that stage.
7. Run `npm run test:scripts:flat`.
8. Move to the next canonical stage only after the current stage's unit tests
   pass.

Do not start by writing broad end-to-end ray-color tests. Integration tests are
useful, but they should come after the unit tests for the stages they exercise.
For example, do not test single-scattered sky color until medium evaluation,
view optical depth, solar transmittance, scattering phase, and single-scattering
accumulation each have known-answer unit tests.

The intended order is the canonical pipeline order:

1. `validateRequest`
2. `resolveRayPath`
3. `sampleViewPath`
4. `evaluateMedium`
5. `integrateViewOpticalDepth`
6. `integrateSolarTransmittance`
7. `evaluateScatteringPhase`
8. `integrateSingleScattering`
9. `resolveSurfaceRadiance`
10. `composeSpectralRadiance`

Process rule: implement and turn stages green in this order. A later stage may
have parked red tests when its expected behavior is already clear, but it
should not become the active implementation target while an earlier physical
stage still has only placeholder behavior unless the user explicitly scopes an
exception.

Current testing rule: each physical pipeline stage should be tested in
isolation first. The stage's direct `runStage(stageId, packet)` tests should
provide the domain known-answer proof. Integration tests should remain
composition/API checks until every physical stage they traverse has isolated
known-answer coverage. Those composition/API checks must include adjacent
producer-to-consumer packet compatibility: field names, array/object shapes,
units, distance semantics, and diagnostic identifiers should be checked through
at least one real stage handoff when both sides of the handoff exist.

When those handoff checks expose a mismatch, tests should pin the one canonical
packet shape rather than tolerating both. The expected shape should be chosen
from the domain contract: what later stages need, which value owns the source
of truth, and which values are cheap and unambiguous enough to derive once and
carry downstream with provenance.

Small helper functions inside a stage, such as phase functions,
Beer-Lambert transmittance, or CIE integration, can have their own direct unit
tests before the stage-level tests use them. If a stage grows into a focused
helper class, move that helper's direct tests into a matching spec file and
keep the integrator stage tests focused on packet input/output behavior.

## Spec Organization

Keep production and helper code files generally below 1000 lines. Spec files
can have a little wiggle room, but do not let the reference pipeline tests turn
into one oversized file.

The current spec split is ownership-based:

- `pipeline-stages.spec.js` owns registry mechanics and any temporary handoff

## `validateRequest`

Purpose: prove the request envelope is physically and numerically well-formed.
This stage compares request data against physical-unit requirements, model
interface requirements, and numerical-control limits. It is not yet a
comparison against atmospheric transport equations.

Current shell location:

- `scripts/flat/atmosphere_rejected/reference/_tests/pipeline-stages.spec.js`, inside
  `describe('validateRequest')`.

Valid input -> canonical output:

- Valid globe model, sorted wavelength grid, normalized ray -> packet contains
  validated model, observer, ray, wavelengths, numerical controls, and no
  diagnostics errors.
- Valid flat model with the same interface names -> passes without any
  globe/flat branch in the integrator.
- Finite nonzero ray direction -> accepted as an orientation vector whose
  magnitude is not physical; the validated request contains a finite unit
  vector so downstream distances remain in kilometers. Source: PBRT Rays for
  the ray origin/direction model, plus the reference code design for our
  kilometer-distance canonicalization.
- Sorted wavelength grid -> preserved in nanometers.
- Request numerical controls over integrator defaults -> merged into the
  validated request without creating shadow defaults.
- Model bundle -> remains the owner of physical constants and geometry/source
  interface methods.
- Extra request fields, including display/report fields and request-level
  physical coefficient fields -> accepted without changing the contracted
  `validatedRequest` fields; generic allowed-property enforcement is deferred
  to future JSON schema validation.
- Original request object -> not mutated.
- Successful packet -> contains `validatedRequest` and stage history.

Invalid input -> named error:

- Missing request object -> error naming `request`.
- Missing observer position -> error naming `observer.positionKm`.
- Invalid observer vector values -> error naming `observer.positionKm`.
- Missing ray direction -> error naming `ray.direction`.
- Ray direction too small to define orientation -> error naming
  `ray.direction`.
- Empty wavelength grid -> error naming `wavelengthsNm`.
- Negative, zero, duplicate, unsorted, or non-finite wavelengths -> error
  naming `wavelengthsNm` and the ordering/positivity problem.
- Missing `world`, `atmosphere`, `solarSource`, or `surface` method -> error
  naming the missing interface method.
- Negative, zero, fractional, string, or non-finite count controls such as
  `viewSteps`, `sunTransmittanceSteps`, `diffuseSkyHemisphereSamples`, and
  `finiteSunSamples` -> error naming the specific `numerical.<field>`.
- Unknown or unrelated extra request fields -> tolerated by stage code. Tests
  may assert the contracted `validatedRequest` fields still have the expected
  values. Generic "only these properties are allowed" tests belong to a future
  standard JSON schema validation layer, not to `validateRequest`.

Validation review findings and progress:

- Near-zero ray direction is covered in the `validateRequest` stage tests,
  because the stage owns the domain rule that a direction must define a usable
  orientation.
- Known numerical number controls reject string values instead of allowing
  coercion. Count controls now reject `0` and fractional values such as `1.5`
  because sample counts must be positive integers.
- Flat-model validation coverage proves method-interface compatibility without
  relying on a `geometryKind` type tag.
- Request-level physical coefficient fields are covered as extra input fields,
  with tests asserting the contracted output fields stay unchanged.
- Placeholder assertions for later stages are scaffold/API coverage, not
  physical validation coverage. They should not be counted as evidence that a
  physical stage has been validated.
- Observer vector shape covers wrong lengths, `null`, `Infinity`, and
  `NaN`, because the domain rule is a finite 3-vector in kilometers.
- Ray direction shape covers wrong lengths, `null`, `Infinity`, and
  `NaN`, because the domain rule is a finite nonzero orientation vector.
- Known numerical number controls reject string values instead of coercing.
- Numerical sample-count controls reject `0` and fractional values because
  `viewSteps`, `sunTransmittanceSteps`, `diffuseSkyHemisphereSamples`, and
  `finiteSunSamples` are positive integer counts.
- Display and reporting controls are accepted as unrelated input extras.
  Spectral radiance remains the physical result; color conversion and report
  shaping are later API consumers.
- Every canonical request-level physical coefficient shadow field is accepted
  when present on input without changing the contracted `validatedRequest`
  fields.
- Flat-compatible model coverage does not require `geometryKind`.
- Single-wavelength grids such as `[550]` are explicitly valid.
- Missing model owner objects are tested separately from missing individual
  methods.
- Integrator default model bundle, numerical controls, and wavelength grid are
  checked for non-mutation.

Completed validation-hardening decisions:

- Distance controls are decided: zero values for `minStepKm` and `maxStepKm`
  are valid, each endpoint rejects if negative, and `minStepKm > maxStepKm`
  rejects.
- Unknown numerical-control keys are not rejected, but are dropped from
  `validatedRequest.numerical` so later stages only see owned controls.
- `integrationMethod` support is registry/implementation-owned. Do not add a
  hardcoded `validateRequest` allow-list. If a real integration-method registry
  exists as the single source of truth, `validateRequest` may validate against
  that registry; otherwise the dispatching stage should fail when no
  implementation exists.

Scaffold/API assertions for placeholder later stages are useful, but they are
not physical validation coverage. Do not count placeholder status checks as
evidence that a physical stage has been validated.

Useful sources: PBRT Rays for origin/direction semantics, Bruneton dimensional
checks, and PBRT's emphasis on explicit medium contracts.

## `resolveRayPath`

Purpose: determine the atmosphere segment and possible surface hit for one
camera ray.

Parameter combinations and expected results:

- Spherical shell, observer at surface radius, zenith ray -> atmosphere entry
  distance is zero, exit distance is approximately atmosphere top height, no
  surface hit.
- Spherical shell, observer above surface, nadir ray -> surface hit occurs
  before atmosphere exit; chosen view path ends at the surface.
- Spherical shell, observer outside atmosphere looking away -> no atmosphere
  segment and no surface hit; downstream stages receive an empty transport path.
- Spherical shell, horizon/grazing ray -> finite positive atmosphere distance
  matching analytic sphere/ray intersection within tolerance.
- Spherical shell, sample-to-ray path through solid Earth -> surface hit records
  occlusion/boundary information for later source visibility tests.
- Flat slab, observer between ground and top, upward ray -> entry zero, exit at
  slab top.
- Flat slab, observer above slab looking upward -> no atmosphere segment.
- Flat slab, observer above slab looking downward -> segment begins at slab top
  and ends at surface if the surface is hit.
- Finite flat disk or bounded local patch, ray exits side boundary -> chosen
  segment ends at the named boundary.
- Large flat disk or bounded patch, near-horizontal ray -> path length follows
  the named lateral boundary rather than a globe horizon approximation.
- Unbounded flat slab, horizontal ray -> loud error naming the missing lateral
  boundary, not an infinite or silently clamped segment.

Starting isolated test inventory, absent implementation:

- `declares its stage contract`: descriptor exposes `requires:
  ['validatedRequest']` and `provides: ['rayPath']`.
- `runs exactly one stage against a prepared path packet`: direct
  `runStage('resolveRayPath', packet)` appends only `resolveRayPath` to
  `stageHistory`, does not mutate the input packet, and writes `rayPath`.
- `fails loudly when prerequisites are missing`: missing `validatedRequest`
  rejects through the descriptor prerequisite check.
- `uses atmosphere intersection as the initial transport segment`: a controlled
  model returns `{ tMinKm: 0, tMaxKm: 10 }`; `rayPath.viewSegment` starts at
  `0`, ends at `10`, and `boundaryReason` identifies atmosphere exit.
- `clips the transport segment to a nearer surface hit`: atmosphere exit is
  farther than a controlled surface hit; `viewSegment.endKm` equals the surface
  distance and `boundaryReason` identifies surface hit.
- `returns an explicit empty path when the atmosphere is not intersected`: the
  controlled atmosphere intersection is `null`; `viewSegment.lengthKm` is `0`,
  downstream sampling can see an empty transport path, and no magic maximum path
  is invented.
- `starts at atmosphere entry for an outside observer`: controlled atmosphere
  intersection has positive `tMinKm`; `viewSegment.startKm` equals entry and
  `viewSegment.endKm` equals exit unless a nearer surface hit applies.
- `clips a behind-observer entry to the observer`: a controlled atmosphere
  interval with `tMinKm < 0` and `tMaxKm > 0` represents the observer already
  inside the medium; the chosen transport segment starts at `0` and exits at
  `tMaxKm`.
- `returns an explicit empty path for an interval entirely behind the observer`:
  a controlled atmosphere interval with `tMaxKm <= 0` contributes no forward
  transport path and must not be converted into a positive segment.
- `returns an explicit zero-length boundary path`: a controlled atmosphere
  interval whose forward segment has zero length reports a finite empty segment
  with boundary metadata, not an invented minimum path length.
- `clips or suppresses atmosphere transport when a surface is before entry`: a
  controlled surface hit before the atmosphere entry distance records the
  surface/boundary result but does not create an atmosphere segment behind that
  surface.
- `rejects inverted or non-finite atmosphere intersection distances`: a
  controlled model returning `tMaxKm < tMinKm`, `Infinity`, or `NaN` fails
  loudly because the interval cannot define an ordered finite path distance.
- `records a named flat lateral boundary`: a controlled flat model reports a
  side-boundary hit before any atmosphere top exit; `boundaryReason` names the
  boundary and the segment ends at that distance.
- `rejects an unbounded flat horizontal path`: a controlled flat model reports
  an unbounded horizontal slab path; the stage throws an error naming the
  missing lateral boundary instead of returning `Infinity` or a clamp.
- `preserves model-owned boundary metadata`: when the model returns a boundary
  label or reason, `rayPath` carries it forward for diagnostics and later
  flat/local-Sun comparison reports.

## `evaluateMedium`

Purpose: evaluate density, extinction, scattering, and absorption at each view
sample.

Scope boundary:

- `evaluateMedium` consumes already sampled camera-ray positions and model-owned
  medium/profile interfaces.
- It may compute sample positions from the validated observer/ray and the
  `viewSamples[*].distanceFromObserverKm` value.
- It must not resolve ray intersections, choose sample distances, integrate
  optical depth, apply Beer-Lambert transmittance, or compute scattering
  radiance.
- Tests for this stage cover only the medium-sample output contract over the
  expected range of valid and invalid inputs. They do not prove that a profile
  adapter, coefficient adapter, CIE dataset, or Earth-atmosphere model is
  correct.
- When a row uses real Earth atmosphere or standard spectral-grid data, those
  values are representative input fixtures. The stage oracle is that
  `evaluateMedium` preserves model-owned diagnostics, aligns arrays,
  derives/sums coefficients, emits vacuum, or rejects invalid model data.
- Expected-range rows should include realistic dense near-surface input,
  low-density high-altitude input, near-boundary input, a named dry-air
  composition payload, and a selected visible-grid shape. Those source rows
  prevent arbitrary stress inputs, but adapter/model correctness belongs in
  adapter/model tests.
- Output shape is chosen by downstream usefulness and unambiguous derivability.
  `evaluateMedium` should emit downstream-ready coefficient totals for
  optical-depth and scattering stages, while recording whether those totals
  were derived from species, direct model totals, or

## `integrateViewOpticalDepth`

Purpose: integrate camera-to-sample and camera-to-end optical depth and
transmittance.

Coverage review for the next analytic pass:

- Sufficient for first red tests: vacuum, zero-length, homogeneous
  Beer-Lambert, empty path, monotonic accumulation, multi-wavelength
  independence, species summation, split-path multiplicativity, and negative
  extinction all have fixture-backed expectations.
- Add before implementation or in the same red-test pass: a nonuniform
  weighted-interval fixture. The stage must integrate sample/interval weights,
  not merely count samples or infer distance from sample count.
- Add before implementation or in the same red-test pass: coefficient shape
  validation. Extinction arrays must align to `wavelengthsNm`; missing,
  too-short, too-long, or scalar-collapsed coefficient data should fail loudly.
- Add before implementation or in the same red-test pass: invalid sample
  weights/distances in a crafted packet. `sampleViewPath` should normally own
  valid samples, but `integrateViewOpticalDepth` is independently runnable and
  must reject negative or non-finite integration weights when tests call the
  stage directly.
- Add handoff coverage once `evaluateMedium` exists: species diagnostics must
  stay as named array entries from `evaluateMedium` into optical-depth
  species diagnostics, and the path-end distance must use the final
  `intervalEndKm` rather than the last midpoint `distanceFromObserverKm`.
- Defer: exponential atmosphere, source-backed Rayleigh optical depths, CIE and
  ASTM full-grid stress, flat large-lateral-boundary transport, and convergence
  sample-count limits. Those require earlier geometry/medium-profile decisions
  or clean external table extraction.

Parameter combinations and expected results:

- Output schema -> explicit camera-to-sample and camera-to-end optical depth
  and transmittance arrays aligned to `viewSamples` and `wavelengthsNm`.
- Input ownership -> the active wavelength grid is
  `validatedRequest.wavelengthsNm` only. Direct stage packets may include stale
  or accidental top-level fields during tests, but this stage must not treat
  those as alternate sources of truth.
- Expected-input extremes -> test the supported boundaries of path length,
  extinction magnitude, optical depth, sample count, wavelength count, and
  species count. These are not random stress tests; each extreme must remain
  inside the domain we expect to support and must still use a sourced equation,
  pinned fixture row, authoritative table boundary, external-tool fixture, or
  local API contract for its expected output. Do not choose optical-depth,
  wavelength-count, path-length, species-count, or sample-count extremes by
  intuition. Use dataset ranges such as CIE/ASTM, atmosphere table extents such
  as PDAS/U.S. Standard Atmosphere, published air-mass/path conditions,
  selected clear-air coefficient models, or convergence studies.
- Vacuum, any path length -> `tau = 0`, `T = 1`.
- Empty transport path -> explicit zero optical depth and unit transmittance
  output, not placeholder or undefined data.
- Homogeneous medium, length `d` -> `tau(lambda) = beta_t(lambda) * d` and
  `T(lambda) = exp(-tau(lambda))`.
- Homogeneous medium with nonuniform interval weights -> `tau(lambda)` equals
  the weighted sum `sum_i beta_t_i(lambda) * ds_i`; for constant extinction this
  reduces to `beta_t(lambda) * sum_i ds_i`.
- Multi-wavelength homogeneous medium -> each wavelength keeps its own
  `tau(lambda)` and `T(lambda)` values without scalar collapse.
- Coefficient arrays must align exactly to `wavelengthsNm`; scalar, missing,
  too-short, or too-long arrays fail loudly instead of being broadcast,
  truncated, or padded.
- Two homogeneous species -> `tau_total = tau_species_a + tau_species_b`.
- Species diagnostics from `evaluateMedium` -> consume the named species array
  shape and preserve species names in per-species optical-depth diagnostics.
- Midpoint samples with interval endpoints -> path-end distance equals the
  final interval endpoint, not the last midpoint sample distance.
- Exponential vertical slab -> numeric `tau` converges to
  `beta0 * H * (1 - exp(-H_top / H))`.
- Homogeneous flat lateral path -> numeric `tau` equals
  `sigma_t * lateralDistance` for the finite named boundary distance.
- Exponential flat near-horizontal path at nearly constant altitude -> optical
  depth is large in proportion to the named lateral distance and local density;
  the test should use a simple fixture with a source-backed or explicitly
  hypothetical lateral boundary rather than an arbitrary stress length.
- Split path `a -> b -> c` -> `T(a,c) = T(a,b) * T(b,c)` within tolerance.
- Longer path with nonnegative extinction -> optical depth is monotonic
  nondecreasing, transmittance is monotonic nonincreasing.
- Zero-length path -> `tau = 0`, `T = 1`.
- Negative extinction from `evaluateMedium` -> loud error; do not clamp.
- Negative, non-finite, or missing sample weight in a directly supplied packet
  -> loud error; do not integrate with invalid distances.

Hardening pass inventory:

- Path-end distance has a positive finite-endpoint case and a negative
  missing/non-finite endpoint case.
- Downstream packet ownership has a positive case proving `mediumSamples` owns
  sample geometry and a negative case proving `viewOpticalDepth` does not
  duplicate sample weights or interval endpoints.
- Species diagnostics have a positive cumulative-output case and a negative
  no-implicit-per-interval-output case.
- Each sourced extreme family needs both a positive and negative case:
  CIE visible grid, ASTM G-173 wavelength grid, clear-air Rayleigh optical
  depth, near-horizon or AM1.5 slant path, flat large lateral boundary,
  selected-model species count, and convergence/sample-count limits.
- Negative sourced-extreme tests should reject malformed inputs, mismatched
  arrays, missing assumptions, arbitrary path multipliers, hidden unbounded
  paths, or unsupported fixture provenance. They should not invent arbitrary
  "too large" values.
- Solar/source visibility and sample-to-source attenuation are negative
  boundary checks for this stage: they belong to `integrateSolarTransmittance`,
  not `integrateViewOpticalDepth`.

Useful sources: PBRT transmittance and Beer-Lambert attenuation, Bruneton
dimensional checks.

## `integrateSolarTransmittance`

Purpose: integrate transmittance and visibility from each view sample to the
active solar source samples.

First fixture-backed and contract-alignment batches status: complete. The
current batch uses controlled solar-source samples and model-owned source-path
segments. It tests the transport math and packet contract only; source
geometry, globe occlusion calculation, flat slab exit calculation, and local
finite-Sun sampling remain model-helper responsibilities.

Parameter combinations and expected results:

- Vacuum, distant directional Sun -> every visible source transmittance is one.
- Homogeneous medium, known sample-to-boundary length -> transmittance equals
  `exp(-beta_t * distance)`.
- Multiple wavelengths over a controlled source path -> each wavelength keeps
  its own optical depth and transmittance.
- Full selected CIE visible grid -> matching coefficient arrays are accepted as
  a grid-shape stress case, while mismatched arrays reject.
- Negative or non-finite source-path transport data -> loud error at this
  stage boundary.
- Model-declared occluded source sample -> visibility remains false and source
  transmittance is zero, without inventing a large optical depth.
- Source sample metadata -> id, direction, source spectrum, weight, and solid
  angle are preserved for downstream scattering and surface-lighting stages.
- Visible selected surface hit -> `solarTransmittance.surfacePoint` carries
  source sample visibility, spectrum, and transmittance for surface radiance.
- Exponential slab, vertical source path -> numeric transmittance converges to
  the analytic vertical optical depth.
- Spherical Earth, sample-to-Sun path intersects solid surface -> visibility
  false and direct source contribution zero.
- Flat slab, source path exits top boundary without surface occlusion ->
  visibility true and finite transmittance.
- Local finite Sun with several source samples -> every source sample preserves
  its direction, solid angle/weight, visibility, and transmittance.
- Local finite Sun, sample inside the solar radius -> loud error or invalid
  visibility according to the source contract; do not produce infinite
  irradiance.
- Multiple wavelengths with Rayleigh extinction -> blue-channel
  transmittance is lower than red-channel transmittance for the same path.

Useful sources: PBRT transmittance, Bruneton Sun visibility/atmosphere path
checks.

## `evaluateScatteringPhase`

Purpose: compute the angular terms that decide how source light scatters into
the camera ray.

Parameter combinations and expected results:

- View ray and source ray in the same direction -> scattering angle/cosine
  matches the selected sign convention and is documented in diagnostics.
- View ray and source ray perpendicular -> cosine is zero and angle is
  `90 deg`.
- View ray and source ray opposite -> scattering angle/cosine matches the
  selected forward/backward convention.
- Rayleigh phase function -> `P(mu) = P(-mu)` and forward/backward values are
  greater than the 90-degree value.
- Rayleigh phase numeric integration over solid angle -> integrates to one
  within tolerance.
- Henyey-Greenstein or Mie approximation with `g = 0` -> isotropic phase value
  `1 / (4 * pi)`.
- Henyey-Greenstein with positive `g` -> forward scattering is greater than
  backward scattering.
- Mie phase numeric integration over solid angle -> integrates to one within
  tolerance for supported `g` values.
- Rayleigh-only fixture -> no Mie phase terms are required.
- Mie-only fixture -> no Rayleigh phase terms are required.
- Future cloud phase fixture -> cloud phase values are added as another
  species term, not folded into the aerosol/Mie term.
- Missing solar transmittance/source sample packet fields -> missing
  prerequisite error; do not recompute hidden source state.

Useful sources: PBRT phase functions and Bruneton scattering-angle diagnostics.

## `integrateSingleScattering`

Purpose: accumulate Rayleigh, Mie/aerosol, and later cloud single-scattered
spectral radiance into the view ray.

Parameter combinations and expected results:

- Zero source -> in-scattered radiance is zero.
- Zero scattering coefficients -> in-scattered radiance is zero even if
  extinction exists.
- Vacuum with no medium -> in-scattered radiance is zero.
- One homogeneous view sample with known `beta_sca`, phase value, source value,
  source transmittance, view transmittance, and step length -> contribution
  equals their product.
- Nonnegative source, coefficients, phase, transmittance, and step length ->
  accumulated radiance is nonnegative.
- Rayleigh-only, equal source spectrum, same path -> shorter wavelengths
  produce greater in-scattered radiance than longer wavelengths.
- Mie-only, wavelength-independent source and coefficient -> wavelength
  variation comes only from configured Mie/extinction/source spectra, not from
  hidden color constants.
- Rayleigh plus Mie fixture -> total single-scattered radiance is the sum of
  the per-species components.
- View transmittance set to zero before a sample -> no contribution from that
  sample reaches the observer.
- Scattering phase stage omitted from the packet -> missing prerequisite error;
  do not silently recompute hidden phase values.

Useful sources: PBRT volume-scattering in-scattering/source-function structure,
PBRT phase functions, and Bruneton single-scattering reference comparisons.

## `resolveSurfaceRadiance`

Purpose: compute radiance leaving a surface toward the camera, then attenuate
it through the view path.

Parameter combinations and expected results:

- No surface hit -> surface radiance component is zero or absent according to
  the packet schema.
- Black Lambertian surface -> reflected radiance is zero for any lighting.
- White Lambertian surface, direct irradiance `E`, normal incidence ->
  `L = E / pi` before view attenuation.
- Lambertian albedo `rho`, direct irradiance `E`, cosine `mu` ->
  `L = rho * E * max(mu, 0) / pi` before view attenuation.
- Source occluded or source transmittance zero -> direct surface contribution
  is zero.
- View transmittance `T_view_end` -> camera-visible surface radiance equals
  surface-leaving radiance times `T_view_end`.
- Diffuse sky disabled -> diffuse term is exactly zero and diagnostics say it
  was disabled.
- Uniform sky radiance fixture, diffuse sky enabled -> hemispherical irradiance
  equals `pi * L_sky`.
- Wavelength-dependent albedo -> spectral surface radiance follows the albedo
  table without RGB conversion.

Useful sources: PBRT diffuse reflection for Lambertian `R / pi` normalization,
PBRT radiometry/reflection background, and the uniform-radiance hemisphere
integral.

## `composeSpectralRadiance`

Purpose: sum all spectral radiance components that reach the observer.

Parameter combinations and expected results:

- In-scattering only -> final spectral radiance equals the in-scattering
  component.
- Surface only -> final spectral radiance equals view-attenuated surface
  radiance.
- Surface plus Rayleigh plus Mie -> final spectral radiance is the
  wavelength-by-wavelength sum of all components.
- All components zero -> final spectral radiance is zero.
- Negative component -> loud error before composition; physical radiance should
  not be repaired by clamping.
- Very bright component -> final spectral radiance may exceed display range;
  no tone mapping or clamping occurs in this stage.
- Component wavelength grids mismatch -> loud error naming the mismatched
  component.

Useful sources: PBRT radiance composition conventions and Bruneton component
diagnostics.

## Reference-Data Tests After Analytic Tests

Do not begin with broad external clear-sky matching. First pass should be
analytic and invariant. Once those pass, add reference-data tests in this
order:

1. Solar spectrum ingestion from NREL/NLR or ASTM G-173 tables.
2. CIE XYZ integration against a tiny pinned table and then the full CIE data.
3. Clear-air transmittance and phase-function behavior against PBRT equations.
4. Globe geometry and CPU/GPU comparison structure inspired by Bruneton.
5. Full clear-sky sanity comparisons against libRadtran or SMARTS-style runs
   after the atmosphere profile, aerosol model, ozone choice, observer altitude,
   solar zenith, and ground albedo are all explicitly pinned.
